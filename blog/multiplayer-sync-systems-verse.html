Multiplayer Sync Systems in Verse: A Developer's Guide

Sixteen players, one shared reality. This is the guide to building sync systems that survive latency, edge cases, and real humans.

By FURY AGENCY • Aug 19, 2026 • Back to Blog

The Multiplayer Problem

Single-player logic is easy: one machine decides everything. Multiplayer is a coordination problem — every player's client runs a simulation, and those simulations must agree. Without explicit synchronization, players will see different winners, teleporting props, and desynced timers.

Server vs Client Authority

The foundational rule of network game design: only one machine may decide. In Fortnite Creative, gameplay devices and Verse scripts run server-authoritatively. Your Verse code is the single source of truth; clients simply render what the server computes. Never let a client-side value (like a local timer) be the decider for round-ending logic.

Replication in Verse

In Verse, values shared across players must be explicitly replicated. The <public> and <transient> specifiers, plus the system functions, control how strongly a change is broadcast. A rule of thumb:

  • Replicate only what players depend on (scores, round state, positions).
  • Avoid replicating decorative or high-frequency data (every particle).
  • Use weak references where possible to avoid keeping actors alive by mistake.
"Every replicated value is a broadcast on a busy highway. Replicate less, and your whole match gets smoother — for every single player."

Broadcasting Events

Device events in Fortnite are broadcast to all clients automatically. The pattern is: server raises the event, every client sees it at (roughly) the same time: 

ScoreManager := GetPlayspace().GetScoreManager()
ScoreManager.GiveScore(Player, 50)   // server-authoritative award

RedTeamScoreUpdatedEvent := RedTeamScore.Set(RedTeamScore.Get() + 50)
RedTeamScoreUpdatedEvent.Subscribe(OnScoreDisplayUpdate)

When both your server logic and your UI subscription react to the same replicated change, everyone's screens stay in lockstep.

Shared State Machines

The cleanest way to keep a whole lobby in sync is a shared state machine — a single variable with strict transition rules:

  • Lobby → players ready up.
  • Countdown → server ticks 3, 2, 1 (server clock, not client).
  • Playing → rules active; server evaluates win/lose.
  • Results → leaderboard + rewards.
  • Back to Lobby → auto-restart for the next round.

Every transition is one replicated variable change; every client's UI reacts to the same transition. This pattern eliminates most "different players in different rounds" bugs at the root. Pair it with a clean race-driven loop from async patterns.

Latency & Race Gotchas

  • Spawn safety: a device that hasn't spawned yet can't receive events. Guard with if Device := Device: before subscribing.
  • Late joiners: handle players joining mid-round — their UI must catch up to current state on spawn, not assume Lobby state.
  • Simultaneous events: two players triggering the same gate must be resolved by the server in a deterministic order (sync before awarding).
  • Resource leaks: every subscription you make with Subscribe should have a matching unsubscribe when the device is destroyed.
